Technical Plan

Modernization Navigator is a local IBM Bob extension for Node.js repo modernization analysis. Bob is the main interface. A local STDIO MCP server runs analysis, writes JSON reports, starts a built-in viewer server, and opens a human-readable static report page.

Node.js + TypeScript Local STDIO MCP Plain HTML/CSS/JS Viewer Stateless npm + pnpm + yarn npm + OSV + internal rules

Technical Requirements

  • Use npm workspaces with apps/* and packages/*.
  • Use tsc for build and tsx for local TypeScript execution.
  • Put all Zod schemas in packages/shared.
  • Infer TypeScript types from Zod schemas. Do not maintain duplicate runtime and compile-time contracts.
  • Keep analysis logic pure where possible. File IO and network IO must stay in thin boundary modules.
  • Keep knowledge base JSON files separate from analysis code.
  • Keep viewer server independent from MCP transport logic.
  • Use eslint and prettier at repo root.

Required Scripts

  • npm run build
  • npm run typecheck
  • npm run lint
  • npm run test
  • npm run viewer:serve
  • npm run viewer:demo-sync
  • npm run mcp:dev

Handoff Outputs

  • Working repo scaffold for all other workstreams
  • Shared report schemas and base types
  • Consistent package naming and import boundaries

Done When

One install command sets up the full repo.
One build command compiles all packages.
Shared schemas are the single source of report truth.

MCP Integration

Owner Unassigned
Job Build the Bob-facing STDIO layer and one custom mode.
Depends On Architecture. Analysis contracts should be stable before final wiring.
Handoff To UI, Demo, Testing

Scope

  • Expose one orchestration MCP tool.
  • Validate inputs and normalize target version handling.
  • Start viewer server and auto-open browser after report generation.

Deliverables

  • Local STDIO MCP server
  • Bob MCP config
  • Bob custom mode: Modernization Architect
  • tool handler for analyze_modernization_target

Detailed Deliverables

  • Local STDIO MCP server
  • Bob MCP config
  • Bob custom mode: Modernization Architect
  • One orchestration tool handler
  • Viewer auto-open integration

Tool Contract

Tool name: analyze_modernization_target

Inputs:
  targetNodeVersion: string
  subdirectory?: string
  offline?: boolean
  autoOpenViewer?: boolean

Outputs:
  reportId: string
  reportPath: string
  viewerUrl: string
  repoRoot: string
  subdirectory?: string
  targetNodeVersion: string
  issueCount: number
  issueCategories: string[]
  externalDataStatus: object

Technical Requirements

  • Use local STDIO transport only.
  • Validate tool input with zod.
  • Accept exact Node versions and major-only versions.
  • Treat the user-requested target version as authoritative.
  • Use repo-declared Node versions only as current-state evidence.
  • Resolve repo root from the Bob-opened local workspace.
  • Restrict analysis to an optional selected subdirectory when provided.
  • Ensure the local viewer server is running before tool return.
  • Auto-open the viewer by default and allow opt-out.
  • Return summary metadata to Bob, not the full raw report.

Custom Mode Requirements

  • Ask for target Node version if missing.
  • Ask for subdirectory only when needed.
  • Call the tool once per analysis request.
  • Respond with current state summary, issues, ordered implementation plan, and validation checklist.
  • Do not promise code patches in MVP.
  • Do not suggest package replacements outside report data.

Handoff Outputs

  • Stable MCP tool contract for Bob integration
  • Viewer URL launch flow
  • Custom mode instructions for demo and docs

Done When

Bob can detect and call the local tool.
Input validation errors are readable and typed.
Viewer opens automatically unless disabled.

Analysis Engine

Owner Unassigned
Job Build scanners, providers, rules, ranking, and report generation.
Depends On Architecture. MCP input shape should be known.
Handoff To MCP, UI, Testing, Demo

Scope

  • Analyze one local Node.js repo or one selected subdirectory.
  • Inspect runtime assumptions, dependencies, CI, deployment config, Docker, scripts, and source code.
  • Generate solution-oriented JSON reports with ranked alternatives.

Deliverables

  • repo scanner
  • provider abstraction layer
  • rule-based ranking engine
  • report writer and history manifest

Inputs

  • Repo root path
  • Optional subdirectory target
  • Target Node version
  • Offline mode flag

Files to Inspect

  • package.json
  • package-lock.json, pnpm-lock.yaml, yarn.lock
  • .nvmrc, .node-version
  • Dockerfile*
  • .github/workflows/*.yml and *.yaml
  • vercel.json, netlify.toml, Procfile
  • shell scripts in common script locations
  • JS/TS source files
  • tsconfig*.json

Detection Modules

  • package manager detection
  • runtime evidence aggregation
  • dependency and lockfile analysis
  • Docker runtime analysis
  • GitHub Actions runtime analysis
  • deployment config analysis
  • shell script runtime analysis
  • source-level API and module-system analysis

Analysis Rules

  • Preserve the repo's detected package manager in generated commands.
  • Support npm, pnpm, and yarn.
  • Use ts-morph for JS/TS AST inspection.
  • Use heuristic scanning for shell scripts, Dockerfiles, YAML, and JSON config.
  • Use npm registry metadata and OSV through provider abstractions.
  • Support explicit offline mode by skipping live calls and continuing with local analysis + internal rules.
  • Use a small internal JSON knowledge base for compatibility and modernization rules.
  • Generate one recommended solution and multiple ranked same-ecosystem alternatives.
  • Do not generate code patches in MVP.

Provider Layer

  • NpmRegistryProvider
  • OsvProvider
  • Typed responses only
  • Network failures isolated from core analysis
  • Caching-ready interface design

Required Report Fields

  • reportId, createdAt, repoRoot, subdirectory
  • targetNodeVersion, detectedPackageManager, offlineMode
  • runtimeEvidence, externalDataStatus
  • issues[] with issue, incompatibility reason, recommended solution, alternatives, files, evidence, commands, validation steps
  • implementationPlan[]
  • validationChecklist[]

Handoff Outputs

  • Stable report JSON contract for UI
  • Issue categories and evidence model for Bob summaries
  • Deterministic output for test fixtures and demo samples

Done When

Works on npm, pnpm, and yarn repos.
Works in offline mode without crashing.
Writes deterministic latest + history + manifest outputs.
Every issue includes reason, solution, alternatives, files, and validation.

Viewer UI

Owner Unassigned
Job Build the local and hosted static viewer plus the built-in local server.
Depends On Architecture and report JSON contract from Analysis.
Handoff To Deployment, Demo, Testing

Scope

  • Render local reports and hosted sample reports in one generic viewer.
  • Support latest report loading and history selection.
  • Serve local assets and report JSON through a built-in Node server.

Deliverables

  • viewer HTML, CSS, and JS
  • local viewer server
  • history selector
  • demo sample config path

Viewer Model

  • Plain HTML, CSS, and JavaScript only
  • One generic viewer page
  • One local data source and one demo data source
  • Light theme only
  • No framework

Local Viewer Requirements

  • Serve viewer assets from a built-in local Node HTTP server.
  • Load report manifest from reports/index.json.
  • Load report detail JSON from latest or history paths.
  • Auto-open local viewer URL after analysis by default.
  • Allow auto-open disable through config or tool input.
  • Support latest report display and history selector.
  • Show repo summary, target version, package manager, offline status, issues, solutions, alternatives, files, evidence, commands, implementation plan, and validation steps.

Hosted Demo Viewer Requirements

  • Deploy static assets only.
  • Use committed sample report data only.
  • No live access to local repo folders.
  • No live MCP connection.
  • Use a demo config file that points to sample manifest JSON.

Local Viewer Server Requirements

  • Implement with Node built-in http.
  • Serve viewer assets and report JSON.
  • Expose a stable local URL.
  • Provide readable error states for missing report files.
  • Support browser auto-open on macOS, Linux, and Windows.

UI Structure

  • Navigation sections: summary, issues, implementation plan, validation, history
  • Collapsible issue cards
  • Copyable file paths and commands
  • History selector without full page reload when practical

Handoff Outputs

  • Stable viewer routes and asset structure for deployment
  • Local server start command for MCP integration
  • Hosted static bundle for judges

Done When

Latest report loads automatically from the local server.
User can switch to previous reports from history.
Hosted demo viewer works with committed sample data only.

Deployment

Owner Unassigned

Depends On UI assets, MCP build output, and sample report generation.
Handoff To Demo & Docs, final submission

Scope

  • Define local setup and build flow.
  • Prepare hosted static viewer deployment.
  • Keep runtime simple: no DB, no backend hosting.

Deliverables

  • local build instructions
  • Bob setup instructions
  • hosted static viewer deployment
  • sample report publish flow

Local Tool Requirements

  • npm install installs all workspaces.
  • npm run build compiles MCP and analysis packages.
  • Bob MCP config points to the built local server entrypoint.
  • Viewer server is part of the repo, not an external global dependency.
  • Core local analysis does not require secrets.

Hosted Demo Viewer Requirements

  • Deploy to Vercel or Netlify.
  • Implementation owner chooses the host.
  • Deploy only static viewer assets and sample reports.
  • Do not expose real local repo paths in sample data.

Operational Constraints

  • No database
  • No backend hosting
  • No live repo access from hosted demo viewer
  • Network access optional for npm and OSV enrichment

Handoff Outputs

  • Public hosted demo URL
  • Repeatable local setup steps
  • Published static sample viewer

Done When

Local Bob integration can be set up from written steps only.
Hosted viewer opens without backend dependencies.
Sample report can be refreshed from a real generated report.
