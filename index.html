Technical Plan

Modernization Navigator is a Bob-first modernization copilot for Node.js repos. Bob owns the conversation, decides what to analyze, chooses which MCP tools to call, compares upgrade paths, and presents the final migration report. The local MCP toolbox gathers deterministic repo evidence, saves report artifacts, and opens the viewer.

Bob-First Experience Adaptive MCP Toolbox Dual Outputs: Chat + Viewer Deterministic Evidence npm + pnpm + yarn Local STDIO Only

Primary Workflow

User works in Bob. Bob asks scope questions, chooses MCP tools, makes the recommendation, saves the report, and opens the viewer.

Real Product Surface

The real product is Bob plus a local evidence layer. No hosted backend, no database, no single giant analysis tool.

Judge Story

Bob is visibly central. MCP makes Bob more exact and scalable by supplying structured repo evidence and persisted artifacts.

Actual Workflow

What Really Happens After the User Prompts Bob

This is the literal runtime path for the Bob-first version. The user sees Bob leading the workflow. MCP stays underneath as the evidence and artifact layer.

1. User in Bob User opens a repo in Bob, selects Modernization Architect, and asks for an upgrade plan.
2. Bob Thinks Bob asks scope questions, inspects the request, and decides which MCP tool to call first.
3. MCP Collects Evidence MCP tools inspect the repo, compare paths, and return structured facts. They do not write the final user report.
4. Bob Decides Bob picks the recommended migration path, persists the artifact, opens the viewer, and presents the final chat report.
User prompt in Bob -> Bob scopes the problem -> Bob picks MCP tools -> MCP returns evidence -> Bob decides the path -> Bob saves report -> viewer opens -> Bob presents the plan
1

User opens Bob and selects the custom mode

Bob is the main product surface from the first click.

User does Open the target repo and choose the mode named Modernization Architect.
Bob does Loads the Bob mode instructions and gets ready to act like a modernization agent rather than a generic coding assistant.
MCP does Nothing yet. MCP is idle until Bob decides what evidence it needs.
2

User asks for upgrade guidance

Example: analyze this repo for Node 22, or compare Node 20 versus Node 22.

User does Provides the target version and any constraint such as safest path or fastest path.
Bob does Asks missing scoping questions if needed: whole repo or subdirectory, direct upgrade or comparison, offline mode, and so on.
Why it matters This is Bob's strength. Bob is deciding what problem to solve, not just forwarding a raw prompt.
3

Bob chooses the first MCP tools

The sequence is adaptive, not hardcoded.

Bob looks at The prompt, repo shape, missing facts, and whether the user wants one path or a comparison.
Bob may call discover_repo_scope, collect_runtime_evidence, and inspect_dependency_blockers.
MCP returns Repo structure, package manager, Node declarations, dependency blockers, and file references as structured evidence.
4

Bob decides whether more evidence is needed

This is where Bob behaves like an agent instead of a static UI.

Bob may notice CI still pins Node 16, Docker uses an older base image, or source code has ESM/CJS friction signs.
Bob may call next inspect_ops_runtime, inspect_source_compatibility, or compare_target_paths.
MCP still does not do The final human recommendation. It only expands the evidence set Bob reasons over.
5

Bob chooses the migration path

Now Bob turns evidence into judgment.

Bob decides Whether to recommend direct upgrade, staged upgrade, one subproject first, or another lower-risk path.
Bob writes The current-state summary, top blockers, chosen path, phased implementation order, and validation checklist.
MCP contributes Hard facts, ranked technical options, and comparable evidence so Bob can justify the decision.
6

Bob saves the artifact

The persisted report includes both evidence and Bob's chosen plan.

Bob calls save_modernization_report after it has chosen the recommendation.
MCP writes reports/latest/report.json, reports/history/<timestamp>.json, and reports/index.json.
Saved content MCP evidence, tool trace, Bob decision summary, Bob execution plan, and validation checklist.
7

Bob opens the viewer

The viewer is a second first-class output, not a replacement for Bob chat.

Bob calls open_report_viewer after the report exists.
MCP does Start or reuse the local viewer server and return the local URL.
User sees A browser view with Bob's recommendation at the top and deep evidence below it.
8

Bob remains in the loop after the first report

The viewer does not end the conversation. Bob keeps helping.

User can ask Focus only on CI blockers, compare Node 20 versus Node 22 again, or explain why Bob chose the staged path.
Bob can do Call more MCP tools, refine the plan, or produce a narrower follow-up summary.
Why this is strong Bob stays the visible agent throughout the workflow instead of disappearing after a single tool call.
Role Split

What Bob Does, What MCP Does, and Why MCP Makes Bob Better

The point of MCP here is not to replace Bob. The point is to make Bob more exact, more scalable across large repos, and more useful for persisted report artifacts and repeatable demos.

Bob Owns

Conversation, scoping, prioritization, target-path comparison, tradeoff judgment, the final user-facing report, and follow-up guidance.

MCP Owns

Deterministic repo inspection, AST/static analysis, compatibility lookups, saved report artifacts, viewer launch, and structured evidence output.

Why Not Bob Alone

Bob can inspect files, but MCP makes repo analysis more exact, repeatable, and artifact-friendly, especially across large multi-area repos.

Why Not MCP Alone

MCP can return facts and comparisons, but it should not own the user conversation or the final migration judgment for this product story.

Bob strength: tool orchestration Bob decides which MCP tool to call next and can vary the sequence by repo shape and user goal.
Bob strength: scoping Bob asks the right question before analyzing the wrong thing: whole repo or one package, direct path or staged path, safest or fastest.
Bob strength: synthesis Bob turns evidence into an actual recommendation, not just a list of findings.
MCP benefit: exact evidence MCP gives Bob stable issue IDs, file references, package facts, CI facts, and source-compatibility evidence.
MCP benefit: persistence MCP saves the report so the viewer, demo flow, and report history all stay deterministic.
Judge-facing value The demo shows Bob as the modernization architect, with MCP visibly improving Bob rather than replacing it.

Plain-English summary: MCP should return evidence. Bob should return conclusions. That is the cleanest version of meaningful Bob usage for this project.

Technical Requirements

  • Use npm workspaces with apps/* and packages/*.
  • Keep all persisted report JSON schemas and MCP tool schemas in packages/shared.
  • Use zod as the source of truth for tool outputs and saved report shapes.
  • Keep viewer server independent from MCP transport logic.
  • Keep report writing independent from evidence gathering.
  • Do not write to the analyzed repo itself.

Handoff Outputs

  • Shared contracts for evidence tools and persisted artifacts
  • Consistent package boundaries for MCP, analysis, and viewer layers
  • A clean separation between Bob decision logic and MCP evidence logic

Done When

One install command sets up the full repo.
One build command compiles all packages.
Shared schemas stay deterministic and reusable across tools and viewer artifacts.

Depends On Architecture and stable tool contracts.
Handoff To Viewer, Testing, Demo

Scope

  • Expose a local STDIO MCP toolbox.
  • Let Bob choose different tool paths for different repo situations.
  • Persist the final artifact and open the viewer after Bob makes the recommendation.

Deliverables

  • local STDIO MCP server
  • Bob MCP config
  • Bob custom mode: Modernization Architect

MCP Tool Inventory

  • discover_repo_scope
  • collect_runtime_evidence
  • inspect_dependency_blockers
  • inspect_ops_runtime
  • inspect_source_compatibility
  • compare_target_paths
  • save_modernization_report
  • open_report_viewer

Design Rules

  • Each tool must do one bounded job.
  • Tools return evidence or side effects, not the final human-facing report.
  • Bob chooses which tools to call and when.
  • save_modernization_report must store both MCP evidence and Bob's decision fields.
  • open_report_viewer must start or reuse the local viewer server and return the viewer URL.

Custom Mode Requirements

  • Ask for target Node version if missing.
  • Ask for subdirectory only when needed.
  • Ask for user preference such as safest path or fastest path when it changes the recommendation.
  • Choose tool order adaptively instead of following one rigid path.
  • Cite MCP evidence in the final report.
  • Persist the report and open the viewer after choosing the plan.

Handoff Outputs

  • Stable Bob-mode behavior that visibly uses Bob's orchestration strength
  • Structured report save flow for the viewer and demo
  • Toolbox story that judges can understand quickly

Done When

Bob can see and call multiple local tools.
Bob can vary the call sequence by repo and request.
The final saved report contains evidence, Bob's decision, and the tool trace.

Evidence Engine

Owner Unassigned
Job Build repo scanners, providers, static checks, and comparison outputs Bob can reason over.
Depends On Architecture and shared tool contracts.
Handoff To Bob + MCP, Viewer, Testing

Scope

  • Analyze one local repo or one selected subdirectory.
  • Inspect runtime assumptions, dependencies, CI, deployment config, Docker, scripts, and source code.
  • Return composable evidence instead of a single final answer blob.

Deliverables

  • repo scanner
  • provider abstraction layer
  • rule-based ranking engine
  • comparison outputs and report-writer support

Files to Inspect

  • package.json
  • package-lock.json, pnpm-lock.yaml, yarn.lock
  • .nvmrc, .node-version
  • Dockerfile*
  • .github/workflows/*.yml and *.yaml
  • vercel.json, netlify.toml, Procfile
  • shell scripts in common script locations
  • JS/TS source files
  • tsconfig*.json

Detection Modules

  • package manager detection
  • runtime evidence aggregation
  • dependency and lockfile analysis
  • Docker runtime analysis
  • GitHub Actions runtime analysis
  • deployment config analysis
  • shell script runtime analysis
  • source-level API and module-system analysis

Output Rules

  • Every issue must have a stable identifier Bob can reference.
  • Every issue must include exact evidence locations, file references, and ranked same-ecosystem options.
  • Comparison results must be machine-readable so Bob can compare direct and staged paths cleanly.
  • Offline mode must skip live calls while keeping local evidence usable.

Handoff Outputs

  • Evidence payloads Bob can cite in the chat report
  • Stable issue categories and file references for the viewer
  • Deterministic outputs for report artifacts and fixture tests

Done When

Works on npm, pnpm, and yarn repos.
Works in offline mode without crashing.
Returns deterministic evidence, issue IDs, and comparison outputs Bob can reason over.
Every finding includes reason, evidence, options, files, and validation.
