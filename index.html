Implementation Handoff

The product is Bob-first. Bob asks questions, decides which MCP tools to call, compares upgrade paths, chooses the recommendation, and writes the final chat report. MCP gathers deterministic evidence, saves the report artifact, and opens the viewer. This page is written so you can assign work without extra explanation.

`01-role.md`

# Modernization Architect Role

You are the modernization architect for this repository.

Your job is to:
- ask for missing scope when it affects the recommendation
- choose which MCP tools to call
- compare direct and staged upgrade paths when needed
- choose the final migration recommendation
- write the final user-facing report in chat

Rules:
- Do not ask MCP to write the final recommendation for you.
- Use MCP only to gather evidence, compare technical paths, save the report, and open the viewer.
- If the target Node version is missing, ask for it before analysis.
- If the repo is a monorepo and no subdirectory is specified, ask whether to analyze the whole repo or one subproject.
- If multiple upgrade paths seem plausible, call `compare_target_paths` before making a final recommendation.
- Cite MCP evidence in your final recommendation.
- Do not invent package replacements outside the current package ecosystem.
- Do not promise code patches in the MVP.

`02-workflow.md`

# Modernization Architect Workflow

Follow this workflow in order:

1. Gather missing scope.
   - Ask for `targetNodeVersion` if missing.
   - Ask for `subdirectory` only if the repo is a monorepo and the request is ambiguous.
   - Ask whether the user wants the safest path or fastest path only if it changes the recommendation.

2. Call evidence tools.
   - Start with `discover_repo_scope`.
   - Then call `collect_runtime_evidence`.
   - Then call `inspect_dependency_blockers`.

3. Decide whether more evidence is needed.
   - Call `inspect_ops_runtime` if CI, Docker, or deployment configuration matters.
   - Call `inspect_source_compatibility` if source-level compatibility risk is likely.
   - Call `compare_target_paths` if both direct and staged upgrade paths are plausible.

4. Choose the migration path.
   - Recommend the best path for this repo and this user request.
   - Use MCP evidence, not guesses.

5. Save the final report.
   - Call `save_modernization_report` with the normalized report object.

6. Open the report viewer.
   - Call `open_report_viewer` with the saved report path.

7. Write the final chat report using this order:
   - current state summary
   - key blockers
   - recommended path
   - implementation order
   - validation checklist
Step 3

MCP Protocol and Fixed Tool Names

Transport Local `STDIO` only.
Message format JSON-RPC 2.0 messages, newline-delimited over `stdin` and `stdout`.
Process model Bob starts the MCP server as a child process.
Module format All server-side workspaces compile to CommonJS for the MVP.
Do not build No HTTP transport, no SSE transport, no browser-only analyzer.

Fixed tool names

  • discover_repo_scope
  • collect_runtime_evidence
  • inspect_dependency_blockers
  • inspect_ops_runtime
  • inspect_source_compatibility
  • compare_target_paths
  • save_modernization_report
  • open_report_viewer
One file in `packages/mcp-server/src/tools/` owns exactly one tool.
Do not rename tool names after shared contracts are created.

Nested schema rules that must be exact

  • `Issue.alternativeSolutions[]` items must include `rank`, `title`, `summary`, `targetVersionRange`, `rationale`, `tradeoffs`, and `commands`.
  • `Issue.evidence[]` items must include `kind`, `filePath`, `summary`, and may include `line`, `column`, `packageName`, `configKey`, `snippet`, and `source`.
  • `externalDataStatus` must contain `npmRegistry`, `osv`, and `notes`.
  • `toolTrace[]` items must contain `toolName`, `purpose`, `status`, `startedAt`, `finishedAt`, and `resultSummary`.
  • `bobExecutionPlan[]` items must contain `phase`, `order`, `title`, `actions`, `dependsOn`, and `validation`.
  • `validationChecklist[]` items must contain `title`, `commands`, and `expectedResult`.

Step 6

Analysis Engine and Providers

`analysis-engine/src/detectors/package-manager.ts`

  • Implement `detectPackageManager(repoRoot)`.
  • Detection order: lockfile, workspace config, `packageManager`, fallback `npm`.

`runtime-evidence.ts`

  • Read `package.json`, `.nvmrc`, `.node-version`, Docker files, GitHub Actions, deployment config, and scripts.

`dependency-blockers.ts`

  • Read manifests and lockfiles.
  • Call providers.
  • Create dependency issues.

`ops-runtime.ts`

  • Check Docker, CI, and deployment runtime mismatches.

`source-compatibility.ts`

  • Use `ts-morph`.
  • Detect deprecated Node APIs and ESM/CJS friction.

`rankers/target-paths.ts`

  • Score direct upgrade and staged upgrade paths.
  • Return `riskScore`, `effortScore`, and blocker summaries.

Providers package

  • `provider-types.ts`: define `NpmRegistryProvider` and `OsvProvider` interfaces.
  • `npm-registry-provider.ts`: fetch npm metadata and support offline mode.
  • `osv-provider.ts`: fetch OSV data and support offline mode.
  • Network failures must not crash full analysis.

Step 11

What "Create the Scaffold" Means

This replaces vague wording like "freeze the folder structure."

  • Create the agreed folders now.
  • Create the agreed files now.
  • Do not move files to different packages after work is assigned.
  • Do not rename MCP tools after work is assigned.
  • Do not rename report fields after work is assigned.
Each dev needs a stable home for their work.
Imports, schemas, and ownership depend on these paths staying stable.
Changing paths mid-implementation creates merge conflicts and broken assumptions.
